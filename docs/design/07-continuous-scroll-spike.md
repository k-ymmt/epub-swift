# 07. 連続スクロールの検証結果

縦の連続スクロール（章をまたいで止まらずに読める表示）を足す前に、`Spikes/` の項目 8・9 で実測した結果。
`00-overview.md` §3 と `04-roadmap.md` は連続スクロールを対象外としているが、後回しにしていただけで、足す予定がある。
§0〜§3 はスパイクの計測とそこから言えること。設計は `08-continuous-scroll.md`、その S1 を実装した後に製品のコードで
測り直した結果は §4（スパイクの結論のうち「macOS だけのちらつき」は §4.2 で訂正した）。

## 0. 実行環境と方法

| 項目 | 値 |
|---|---|
| macOS | 27.0.1、Apple Silicon、ウィンドウ 390×760 pt。指（トラックパッド）でのスクロールは測っていない |
| iOS | iOS Simulator 27.2、iPhone 17（402×874 pt、@3x）。実機では測っていない |
| 本 | `Tests/Fixtures/moby-dick.epub`（線形 spine 142 項目、Web フォント入り） |

- 試した構成: WKWebView 1 つ。メインフレームは `epub://spike/…` のラッパー文書で、これが縦にスクロールする（iOS では WKWebView 自身の
  `UIScrollView`）。章ごとに同一オリジンの `<iframe scrolling="no">` を 1 つ置き、高さを章の内容の高さに合わせる
  （`Sources/SpikeKit/ContinuousScrollJS.swift`）。縦書き見開きのラッパー（02-rendering、スパイク 6）と同じ仕組みを縦に並べたもの。
- 章には多段組を外す CSS を注入した（`BookFixture.scrolledCSS`: `html { height: auto; overflow: hidden }`、本文は 17 px / 行間 1.6 / 左右 24 px）。
- 実行: `cd Spikes && SPIKE_WINDOW_FLOATING=1 swift run -c release spike-run --out output/continuous-scroll 8`（macOS）、
  `OUT=$PWD/output/continuous-scroll/ios scripts/run-ios.sh 8`（iOS）、
  `OUT=… SPIKE9_MODE=runway SPIKE9_PRESET=0 SPIKE9_SECONDS=60 scripts/run-ios.sh 9`（iOS、記録中に外からスワイプを入れる）。
- メモリは WebContent / GPU プロセスの `phys_footprint`（`proc_pid_rusage`）。
- 位置の安定は、画面上端付近の要素の位置（JS）と、上端 48 pt の帯のスナップショット（約 130 回 / 秒）の両方で見た。
  帯のスナップショットが 1 枚でも変われば、1 フレームだけのちらつきも数に入る。
- 指でのスクロール（項目 9）は、スクロールビューのオフセットと画面全体のスナップショットを約 107 回 / 秒で記録し、
  連続する 2 枚の絵が何 pt ずれたかを行ごとのインク量から求めて、オフセットの変化と突き合わせた（`scripts/analyse-fling.py`）。
- macOS のウィンドウは、他のウィンドウに隠れたり画面がロックされたりするとページが `hidden` になり、`requestAnimationFrame` が
  止まって、フレームを待つフェーズが進まなくなる。`SPIKE_WINDOW_FLOATING=1` で最前面に固定して測った。

出力: `Spikes/output/continuous-scroll/results-macos.md`、`…/ios/results-ios.md`（項目 8 の全ログ）、
`…/ios-fling-*/analysis.txt`（項目 9 の各記録の解析。元の記録 `spike9-*.json` は大きいので管理外）。

## 2. 詳細

### 2.1 メモリと読み込み時間

読み込んだ章の数と WebContent プロセスの増分（空のラッパーとの差）。iOS の GPU プロセスは章の数によらず +3.1 MB。

| 章の数 | 合計の高さ（iOS） | WebContent 増分（iOS） | WebContent 増分（macOS） |
|---|---|---|---|
| 1 | 10,677 px | +4.7 MB | +30.1 MB |
| 3 | 14,216 px | +5.9 MB | +14.9 MB |
| 7 | 49,441 px | +11.9 MB | +34.0 MB |
| 15 | 100,546 px | +20.0 MB | +27.1 MB |
| 31 | 201,329 px | +38.3 MB | +44.9 MB |
| 63 | 376,065 px | +68.9 MB | +74.9 MB |
| 142（全章） | 742,978 px | +138.5 MB | +146.8 MB |

macOS の値は章の数に対して単調でない（1 章で +30 MB、3 章で +15 MB）。読み込み直後の一時的な確保が残っている時点で読んで
いるためとみられ、切り分けていない。macOS の GPU プロセスは 13〜69 MB の間で上下し、章の数との関係は見えなかった。

全章を順に足したとき:

| | iOS Simulator | macOS |
|---|---|---|
| 所要 | 2.03 秒 | 1.03 秒 |
| 1 章の読み込み（`src` 設定 → `load`）| 中央 2 ms / 95% 5 ms / 最大 1,135 ms | 中央 1 ms / 95% 4 ms / 最大 132 ms |
| 1 章の高さの計測（強制レイアウト） | 中央 1 ms / 95% 3 ms / 最大 6 ms | 中央 1 ms / 95% 4 ms / 最大 43 ms |
| 文書の高さ（フォント適用後） | 742,978 px（画面 850 枚分） | 767,482 px |
| 25 / 50 / 75 / 99% へスクロール | 描画される（インク率 0.07〜0.12）、メモリは 154.2〜154.4 MB のまま | 描画される（インク率 0.09〜0.13）、メモリは 165〜174 MB |

最大の 1,135 ms は新しい WebContent プロセスが最初の文書を読むときの値で、2 つ目以降には出ない。
章の高さは中央 4,526 px、95% 15,815 px、最大 28,974 px（`load` 時点）。

巨大な章（最長の章の本文を 20 回繰り返した 908 KB の文書）: iOS で計測 56 ms、高さ 578,714 px、+31.6 MB。
macOS で読み込み 22 ms、計測 67 ms、高さ 601,552 px、+56.1 MB（60% へ飛んだ後は +41.7 MB）。どちらも 60% の位置まで飛んで描画された。

言えること: 高い iframe でも描画コストは見えている範囲だけにかかる。メモリは読み込んだ DOM の量にほぼ比例するので、
章の窓（前後の数章）を持てば一定に収まる。1 章が巨大でも成り立つ。

### 2.2 フォントの適用で高さが変わる

`load` の時点では本の Web フォントがまだ当たっておらず、その後に章の高さが変わる。iOS では 813,123 px → 742,978 px（91.4%）、
142 章中 139 章が変わった。macOS も 840,588 px → 767,482 px（91.3%）、140 章。項目 9 の記録では、変化は `load` の 0〜10 ms 後に来た。

各章の `documentElement` を `ResizeObserver` で見て、iframe の高さを合わせ直す必要がある。「上の章の高さが後から変わる」は
画像の遅延などのまれな場合ではなく、章を読み込むたびに起きる。

画面外に置いた iframe で先に測った高さ（`measureOnly`）は、`document.fonts.ready` を待ってもフォント適用前の値のままだった
（28,974 px と出て、実際は 26,446 px）。待ち方が足りないのか、画面外の iframe ではフォントが読まれないのかは突き止めていない。
事前に測った高さは「だいたい合う見積もり」として扱い、読み込み時の補正を前提にする。

### 2.3 位置の安定（静止中）

画面より上で起きた変化のあと、読んでいた行が何 px 動いたか（最大値）。表は iOS。「上に章を足す」は 5 章、それ以外は 3 章で試した。
0 px の行は、帯のスナップショット（1 試行あたり約 100 枚）も 1 枚も変わっていない。

| 上で起きた変化 | アンカリング任せ | `scrollBy` で補正（manual） | 余白で補正（runway） | 補正なし（対照） |
|---|---|---|---|---|
| 章を足す（高さを知らずに） | 12,682 px | 0 px | 0 px | 12,682 px |
| 章を足す（見積もりの高さを先に与える） | 12,682 px | 0 px | 0 px | — |
| ラッパー自身に 500 px の `div` を足す | 500 px | 0 px | 0 px | — |
| 上の章が後から 300 px 伸びる | 300 px | 0 px | 0 px | 300 px |
| 読んでいる章の、画面より上が 300 px 伸びる | 300 px | 0 px | 0 px | 300 px |
| 上の章を外す（下に続きがある） | 12,682 px | 0 px | 0 px | 12,682 px |
| 上の章を外す（文書の最下端にいる） | 0 px | 11,329 px | 0 px | 0 px |

- **アンカリング任せは対照と同じ値**で、iframe ではないただの `div` を足しても同じだった。WebKit のソースでは
  `CSSScrollAnchoringEnabled` は既定で有効だが、この構成（WKWebView のメインフレーム、iOS 27.2 Simulator）では働かなかった。
  原因は未特定。頼らない。
- manual と runway は同じ規則で動く。画面上端付近の要素を 1 つ覚えておき、レイアウトがそれを動かした分だけ戻す。
  manual は `window.scrollBy` で戻し、runway は先頭に置いた空のブロック（余白）の高さを同じだけ変えて戻す。
- 要素の位置は**文書座標**（ビューポート内の位置 + `scrollY`）で比べる。ビューポート内の位置で比べる版は、スクロール中に
  同じ補正を 2 回かけた（−2,528 px のところで +26,559 px 動いて画面が空白になった）。
- 最下端で上の章を外す行: 文書が縮むとスクロールビューが位置を新しい最下端に切り詰め、それだけで行は動かない。
  manual はそのうえでもう一度補正して飛ぶ。runway は章を外すのと同じレイアウトの中で余白を章の高さだけ伸ばすので、
  文書が縮まず、切り詰めも起きない（余白を後から伸ばす最初の版は 12,682 px 飛んだ）。

macOS も同じ結果だった（試した章が違うので、対照のずれは 12,682 px でなく 4,227 px。manual と runway は全行 0 px、最下端で
上の章を外す行は manual だけ 4,227 px）。**違いは 1 つだけ**: 「読んでいる章の、画面より上が 300 px 伸びる」で、最終のずれは
0 px だが、途中で帯のスナップショットが変わった（manual 7/495、runway 14/506。3 試行の合計なので、1 試行あたり 2〜5 枚）。
伸びた 300 px が一度描かれてから補正が効いている。上の章（別の iframe）が伸びる場合は 0 枚で、iOS はどちらも 0 枚。
`ResizeObserver` を章の文書の側で作る版も試したが変わらなかった（manual 13/519、runway 11/525）。原因は §4.2（スナップショットの
撮り方。画面には出ていない）。

### 2.4 指と慣性でスクロールしている最中（iOS）

章の窓を自動で動かしながら（先読み 2,000 px）、下向きのスワイプを 3 回ずつ間隔を空けて入れた。スクロールの速さは
最大で 1 標本あたり 110〜130 pt（およそ 12,000〜14,000 pt / 秒）。各条件 1 回ずつの記録。

| 方式 | 高さ | スクロール中に上に入った章 | スクロール位置の書き換え | 空白の画面 | 補正の抜け |
|---|---|---|---|---|---|
| manual | 見積もりあり | 58（28,974 → 26,446 px）と、その読み込み完了と同時に 57（6,021 → 5,532 px） | 4 回 | 1 回（5 標本、27 ms。874 pt 中 812 pt が白） | なし |
| manual | なし | 58 と、その読み込み完了と同時に 57 | 3 回 | 1 回（2 標本、6〜25 ms） | **1 回（章 58 が 2,528 px 縮んだ分）** |
| runway | 見積もりあり | 58 | 0 回 | 0 回 | なし |
| runway | なし | 58 | 0 回 | 0 回 | なし |

manual が破綻する理由はページのログに出ている。指や慣性でスクロールしている間、スクロール位置は UI プロセスが決めて
WebContent に送ってくる。`scrollBy(0, 28974)` の直後、ページの `scrollY` は 30,913 になるが、その前に UI プロセスが送った
位置で上書きされて 1,879 に戻り、少しして 30,793 になる。戻っている間、ページは次のように振る舞う。

1. 自分が文書の先頭近くにいると判断して、要らない章 57 をすぐ読み込む（runway ではこの章は読み込まれていない）。
2. その位置のタイルを描くので、実際に見えている 30,000 px 付近が数フレーム白くなる。
3. 「画面上端の要素」を古い位置で選び直す。高さなしの記録では、選び直した要素が章 58 の中にあったため、章 58 が
   フォントで 2,528 px 縮んだときに補正が走らなかった。加えた補正の合計は 34,506 px、必要だったのは 31,978 px で、
   読んでいた行は 2,528 px ずれたままになった。

最初の +28,974 px の補正そのものは、指が触れている最中でも絵が指の速さで動き続けた（+60 → +0 → +60 pt / 標本）。
壊れるのは、補正の直後にもう一度ページが位置を読んだり書いたりしたときである。

runway はスクロール位置を一切書かない。章 58 が入ったとき余白が 28,974 px 縮み、続いて 2,528 px 伸び、その間
オフセットは指の動きだけで変わり続けた。絵がオフセットの言う位置に無い標本は、どちらの記録でも 0（オフセットと
スナップショットを読む時刻の差による 1 標本の遅れと、1 pt の丸めを除く）。

### 2.5 測れていないこと

- 実機での滑らかさ（フレーム落ち、タイルの描画が追いつく速さ）。ここまでは全部 Simulator。
- macOS でトラックパッドの慣性スクロール中に上へ章が入る場合（スワイプを注入する手段が無く、測っていない）。
  スクロール位置を誰が持つかが iOS と違う可能性があり、`scrollBy` 方式の破綻が macOS でも起きるかは分からない。
- macOS の、読んでいる章の中で上が伸びたときのちらつき（2.3）の原因と直し方。
- 極端に速いスクロール。スワイプを 10 回以上続けて約 50,000 pt / 秒まで加速させた記録（manual）では、画面の大半が白い
  標本が続いた。タイルの描画が追いつかないのか、補正の破綻なのかは切り分けていない。runway では試していない。
- 余白が足りなくなったとき（見積もりより上の章が長い）。スパイクは足りない分を `scrollBy` で補うが、スクロール中に
  それが起きた場合は 2.4 と同じ危険がある。静止しているときに余白を足し直す処理は書いていない。
- 本の先頭に着いたときに余った余白を消す処理、末尾側（下に章を足す・外す）での同じ記録。下に足す場合は読んでいる行より
  下が伸びるだけなので補正は要らないはずだが、指でのスクロール中の記録は取っていない。
- 文書の高さの上限。余白を本全体の見積もりにすると、長い本では数百万 px になる。WebKit がどこまで扱えるかは未確認。
- スクロールアンカリングが効かない原因、画面外の iframe でフォント適用後の高さを得る方法（2.2）。

## 3. ここから言えること

設計を決めるときの材料として。

1. **WKWebView 1 つ + ラッパー文書 + 章ごとの iframe で成り立つ。** メモリは読み込んだ章の数に比例し、描画は見えている所だけ。
   章の窓を 7〜15 章に保てば、本の長さによらず +12〜20 MB 程度で済む（iOS Simulator の値）。
2. **スクロールアンカリングには頼らない。** `overflow-anchor: none` にして自分で補正する。
3. **スクロール中にスクロール位置を書かない。** 先頭に余白を置き、上に章を足す・上の章の高さが変わる・上の章を外すときは
   余白の高さで帳尻を合わせる。余白は「まだ読み込んでいない上の章の高さの見積もり」にすれば、スクロールバーの位置が
   本全体の中の位置を表す。見積もりの誤差の清算（余白の足し直し、先頭での切り詰め）は静止しているときに行う。
4. **補正量は文書座標で求める。** スクロール中の `scrollY` は古い値に戻ることがあるので、ビューポート内の位置を
   比べてはいけない。窓を動かす判断（先読みが足りないか）にも同じ注意が要る。
5. **上の章を外すときは、同じレイアウトの中で余白を先に伸ばす。** 文書が一瞬でも縮むと、最下端付近でスクロール位置が
   切り詰められる。
6. **章の高さは読み込み後に変わるものとして作る。** 各章を `ResizeObserver` で見る。事前計測やキャッシュの高さは見積もり。
7. 位置（CFI）、検索、注釈は EPUBCore の側にあり、この構成の影響を受けない。ページ番号に依存する部分
   （`ReaderSession`、`BookPagination`、`PaginationService`）をスクロール表示でどう扱うかは別に決める必要がある。

## 4. S1 の実測（製品のコード、2026-11-14）

`08-continuous-scroll.md` の S1 を実装した後、スパイクのコントローラでなく `ReaderSession` と `reader.js` のスクロール
コントローラで測り直した。環境は §0 と同じ（macOS 27.0.1、iOS Simulator 27.2 の iPhone 17）。実機では測っていない。

### 4.1 方法

- **macOS、静止中と操作中の位置の安定**: `EPUBRendererTests` の `ScrollStabilityTests`。読む行の文字の位置をフレームごとに読み、
  帯（幅いっぱい × 48 pt）の絵を変化の間じゅう撮り続ける。帯は `takeSnapshot` でなくウィンドウサーバーから読む（§4.2）。
  1 秒あたり約 70 枚。
- **macOS、トラックパッド**: `ScrollWheelTests`。位相と慣性の位相を持つホイールイベントを合成して WebView に渡す。
  ReaderDemo の記録モードにも同じ合成（Debug メニューの「Record 20 s of trackpad flings」）がある。本物のトラックパッドの
  慣性の曲線ではない。
- **iOS、指と慣性**: ReaderDemo の記録モード（`Examples/ReaderDemo/README.md`）で Moby-Dick を章 40 から開き、Simulator に
  スワイプを注入して、`Spikes/scripts/analyse-fling.py` で読んだ。1 秒あたり約 40 標本。スワイプは下向き（上の章が入る向き）を
  中心に、間を空けた場合と、続けて入れて加速させた場合。

### 4.2 macOS の「ちらつき」は撮り方による見かけ

スパイクは「読んでいる章の中で読む行より上が伸びると、macOS だけ帯のスナップショットが数枚変わる」ことを、伸びた分が一度
描かれてから補正が効いている、と読んだ（§2.3）。製品のコードでも、負荷の高いとき（全テストを並列に走らせたとき）に
13 枚中 1 枚が変わった。原因は次のとおりで、画面には出ていない。

- macOS の `WKWebView.takeSnapshot` は、画面に出ている絵を写すのではない。要求が届いた時点で WebContent プロセスが
  レイアウトを済ませ、ページをビットマップに描いて返す。
- 章の中のブロックが伸びると、次のフレームのレイアウトで文字が下がり、**同じフレームの中で** `ResizeObserver` が章の iframe の
  高さと上の余白を直してから描画される。画面に出るフレームでは文字は動かない。
- スナップショットの要求が「変化の後、次のフレームの前」に届くと、そこでレイアウトが強制され、`ResizeObserver` がまだ動いて
  いない状態（伸びた分だけ文字が下がっている）が描かれる。どのフレームにも無い絵である。
- iOS の `takeSnapshot` は UI プロセス側のレイヤーを写すので、この現象は起きない（スパイクで iOS が 0 枚だったことと合う）。
  別の iframe（上の章）が伸びる場合に 0 枚だったのも説明がつく: 上の章の iframe は高さが固定なので、`ResizeObserver` が
  動くまで帯の中の絵は変わらない。

確かめ方: 変化（章 8 の先頭に 333 px のブロックを足す / 外す）の直後にページを 150 ms 止め、その間にスナップショットを要求した。
返ってきたスナップショットは前の絵と画素の 20〜21% が違い、同じ 0.4 秒の間にウィンドウサーバーから読んだ絵（1 回あたり
26〜45 枚）は 1 枚も変わらなかった（4 回とも）。ふつうに伸び縮みさせた 6 回でも、ウィンドウの絵は 1 枚も変わらなかった
（1 回あたり 26〜44 枚）。ウィンドウの絵が動きを写せることは、7 px スクロールすると帯の 33% が変わることで確かめてある。

これを受けて、`ScrollStabilityTests` の帯はウィンドウサーバーから読むように変えた（`CGWindowListCreateImage`。自分の
プロセスのウィンドウなので画面収録の許可は要らず、他のウィンドウに隠れていても写る）。macOS の記録モードは今も
`takeSnapshot` なので、記録の「絵が合わない標本」には同じ見かけが混ざる。

### 4.4 測れていないこと

- 実機（滑らかさ、描かれないコマが実際にどう見えるか、指が触れたままのジャンプ、本物のトラックパッドの慣性）。
- 窓の上限（24 章）で、指や慣性の最中に章が外れる場合。記録ではそこまで長くスクロールしていない。
- 非表示の WebView で測った高さの正しさ（計測は S3）。
- スクロールアンカリングが効かない原因（使わないので調べていない）。
