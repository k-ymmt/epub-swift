# 08. スクロール表示（連続スクロール）

章をまたいで縦に読み続けられる表示の設計。ページめくり（以下「ページ表示」）と並ぶもう 1 つの表示方式として足す。
方式の根拠は `07-continuous-scroll-spike.md` の実測。2026-11-14 設計。**S1（スクロールで読める）は同日に実装済み**で、
設計と違えた点と §14 の実測の結果は §16 にまとめてある。S2 以降は未実装（本文の該当箇所に「S2」「S3」と書いてある）。

## 0. 決定事項

利用者が決めたこと（2026-11-14 の質問）。

| 項目 | 決定 |
|---|---|
| 位置づけ | 切り替え式。`ReaderSettings` に表示方式を足す。ライブラリの既定はページ表示のまま |
| 対象の本 | 横書きリフローだけ。縦書きの本と固定レイアウト（FXL）の本は、スクロールを選んでいてもページ表示で開く |
| OS | iOS と macOS の両方 |
| ページ番号 | 表示領域 1 枚分の高さを 1 ページと数える。`BookPagination`、進捗スライダー、ページ指定の移動はそのまま使う |
| 端のタップ | スクロールしない。どこをタップしても中央のタップとして扱う |
| 章の境目 | 一定の余白を挟んで続ける。区切り線も改ページも入れない |
| 広い画面 | 中央に 1 段。本文の最大幅は文字サイズに比例し、`ReaderSettings` で変えられる。`spreadPolicy` は無視する |
| スクロールインジケータ | 出さない |
| キー（macOS） | ↑ ↓ は数行分。space / PageDown / → は 1 画面分進み、⇧space / PageUp / ← は戻る。Home / End は章の先頭 / 末尾 |
| 横スワイプ | 何もしない |
| 画面の端 | 本文はバーや安全領域の下まで流れる（iOS、macOS とも）。読み始めの行と位置の復元は、アプリが渡す上下のインセットの内側に置く |
| 本の末尾 | ふつうのスクロールと同じく、最後の行が表示領域の下（下のインセットの上）に来た所で止まる。そこでは最後のページ・100% と数える。本の後ろに空白は足さない（§6.1） |
| 方式の切り替えの往復 | 位置は切り替え先の規則で取り直す。スクロール → ページ → スクロールと往復すると、読む行は最大で 1 ページ分上に戻ってよい（§7） |
| 実機での確認 | 最初のマイルストーン（S1）の直後に、利用者が手で確かめる。問題があればそこで方式を見直す |

アプリ（Laperm）側の決定は Laperm の ADR 0056 の追記に書く。

## 1. 範囲

- スクロール表示になるのは、次を全部満たす本。
  - 固定レイアウトの spine item を 1 つも含まない。
  - `page-progression-direction` が `rtl` でない。
  - 読み込んだ章が縦書き（`vertical-rl` / `vertical-lr`）でない。
- 最後の条件は章を読むまで分からない。スクロール表示で読み込んだ章が縦書きだと分かったら、セッションはその本をページ表示に
  切り替え、`position` の CFI を保って読み直す。同じセッションの間は戻さない。
- どちらで表示しているかは `ReaderSession.layout` で分かる（§3.2）。アプリは `settings.layout == .scrolled` なのに
  `session.layout == .paged` の本で「この本はページ表示のみ」と示せる。
- 線形でない spine item（`linear="no"`）は流れに入れない。リンクや `go(toSpineIndex:)` で開いたときは、その文書 1 つだけの
  スクロール文書として見せ、スクロールで前後の章へは続かない（ページ表示で単独の章として開くのと同じ扱い）。
- ページ表示の動作は変えない。

## 2. 用語

| 用語 | 意味 |
|---|---|
| スクロール文書 | ライブラリが生成するラッパー文書。メインフレームが縦にスクロールし、章ごとの iframe を縦に並べる |
| 窓 | スクロール文書に読み込んである、連続した章の並び |
| 上の余白（runway） | 窓の先頭の章の上に置く空のブロック。高さは「窓より前の章の高さの合計」 |
| 下の余白 | 窓の末尾の章の下に置く空のブロック。高さは「窓より後の章の高さの合計」 |
| 先頭 / 末尾の境界 | 上の余白の前と下の余白の後に置く空のブロック。高さは上 / 下のインセット。本の最初の行を読む行に、最後の行を下のインセットの上に置けるようにする |
| 読む行 | 表示領域の上端から上のインセットだけ下がった位置。位置（CFI）とページ番号はこの行で決める |
| 静止 | 読者の操作（指、慣性、トラックパッド、ホイール）もプログラムのスクロールも進んでいない状態（§5.6）。スクロール位置を書いてよいのはこのときだけ |
| ページの高さ P | 表示領域の高さから上下のインセットを引いた値。スクロール表示の 1 ページ |

## 3. 公開 API

### 3.1 `ReaderSettings`

```swift
public enum ReaderLayout: String, Codable, Hashable, Sendable {
    case paged          // ページ表示（既定）
    case scrolled       // スクロール表示
}

public struct ReaderSettings {
    public var layout: ReaderLayout = .paged
    public var scrolledTextWidth: Double = 36    // スクロール表示の本文の最大幅。本文の文字サイズの倍数（em）
}
```

- `scrolledTextWidth` は本文の基準の文字サイズ（`fontScale` を掛けた後）に対する倍数。36 は欧文でおよそ 70 字、和文で 36 字。
  表示領域がこれより狭ければ、幅は表示領域から左右の余白（`pageMargins.horizontal`）を引いた値になる。
- `pageMargins.horizontal` は本文の左右の余白。`pageMargins.vertical` は章の上下の余白に使う（§4.2）。
- `spreadPolicy` はスクロール表示では使わない。
- どちらも `layoutKey` に入る（§6.3）。`layout` の無い古い JSON は `.paged` で読む。

### 3.2 `ReaderSession`

```swift
extension ReaderSession {
    public private(set) var layout: ReaderLayout       // 今この本を表示している方式（§1）
    public var contentInsets: ReaderInsets             // 上下のインセット（pt）。EPUBReaderView が設定する
    public private(set) var isScrolling: Bool          // 読者のスクロールが続いている間 true（S2。S1 には無い）
}

public struct ReaderInsets: Hashable, Sendable {
    public var top: Double = 0
    public var bottom: Double = 0
}
```

既存のプロパティは、スクロール表示では次の意味になる。

| プロパティ | スクロール表示での意味 |
|---|---|
| `position` | 読む行にある最初のテキストの CFI（§7） |
| `currentSpineIndex` | 読む行のある章 |
| `visibleSpineIndices` | 表示領域（インセットの内側）に一部でも入っている章。読み順 |
| `currentPageIndex` / `chapterPageCount` | 読む行のある章の中の仮想ページと、その章の仮想ページ数（§6.1） |
| `currentPage` / `visiblePages` | 書籍全体の仮想ページ。`visiblePages` は表示領域に一部でも入っているページで、ふつう 2 つ |
| `chapterProgression` / `totalProgression` | ページ表示と同じ計算（`BookPagination.progression`） |
| `isAtStart` / `isAtEnd` | 最初の章の先頭 / 最後の章の末尾までスクロールしている |
| `isShowingSpread` / `isZoomed` | 常に false |
| `relayoutSnapshot` | ページ表示と同じ（再レイアウトと窓の作り直しの間だけ非 nil。§11） |
| `pageSnapshot(_:)` | 常に nil（めくり演出が無い） |

移動の API:

| API | スクロール表示での動作 |
|---|---|
| `go(to:)`（CFI、`ReadingPosition`、目次、検索結果）、`go(toSpineIndex:)`、`go(toPage:)`、`go(toPageInChapter:)` | 行き先を読む行に合わせる（§8.1）。アニメーションなし |
| `goForward()` / `goBackward()` | 1 画面分（P から重なり分を引いた量）をアニメーションでスクロールする（§8.2） |

### 3.3 `ReaderEvent`

```swift
public enum ReaderEvent {
    case scrolling(Bool)        // 読者のスクロールが始まった（true）/ 止まった（false）。ReaderSession.isScrolling と同じ値
}

public struct ReaderNavigation {
    public enum Cause { case pageTurn, jump, link, scroll }   // scroll を追加
}
```

`scrolling(_:)` と `navigated(cause: .scroll)` は S2 で足す（S1 では、読者のスクロールで出るのは `positionChanged` だけ）。

- `scrolling(true)` は、指・慣性・トラックパッド・ホイール・↑ ↓ キーによるスクロールで本文が動き始めたときに 1 回出る。
  `go(to:)` 系と `goForward()` / `goBackward()` では出ない。アプリはこれでバーを隠し、矩形に結び付けたポップオーバーを閉じる。
- `scrolling(false)` は読者のスクロールが終わったとき（§5.6 の静止。指を置いたまま止めている間は終わっていない）。その前に
  `positionChanged` が出て、可視ページが変わっていれば `navigated(cause: .scroll, from:, to:)` が出る。
- `navigated` の `pageTurn` は `goForward()` / `goBackward()`、`jump` / `link` はページ表示と同じ。
- `positionChanged` はスクロール中にも出るが、1 秒に 1 回まで。止まったときには必ず出る。
- `tapped(_, zone:)` の `zone` は常に `.center`。`imageTapped` は位置によらず常にアプリへ渡す（めくりに使う帯が無い）。
- 矩形（`SelectedText.rects`、`annotationTapped` の `rects`、`NoteContent.sourceRect`、`TappedImage.rect`、
  `rects(for:)`）は `EPUBReaderView` の枠の座標で、イベントの時点のもの。スクロールすると古くなる。

### 3.4 EPUBUI

```swift
extension View {
    public func readerContentInsets(top: Double, bottom: Double) -> some View
}
```

- `EPUBReaderView` はこの値を `ReaderSession.contentInsets` に入れる。既定は 0。ページ表示では使わない（アプリが今までどおり
  枠の大きさで決める）。
- スクロール表示では、アプリは `EPUBReaderView` をバーや安全領域の下まで広げて置き、隠れる分をこの修飾子で渡す。
  本文は枠の端まで流れ、読む行・位置の復元・1 ページの高さはインセットの内側で数える。
- インセットを変えるとページの高さ P が変わる。P は画像の高さの上限（§4.2）に使うので、窓の章を組み直し、高さの計測も
  新しい P でやり直す（§6.3、§11）。アプリは、バーの出し入れのたびにインセットが変わる作りにしない。
- `pageTransition` はスクロール表示では使わない。`ReaderGestures` は `keyboardEnabled` だけが効く（`swipeEnabled` と
  `tapToTurnEnabled` は無視）。
- `ReaderProgressSlider` は変えない。仮想ページの番号で今までどおり動く。

## 4. 構成

### 4.1 WebView とスクロール文書

表示用の WKWebView は 1 つのまま、ページ表示と同じものを使う。スクロール表示では次のように設定する。

- フレームは `EPUBReaderView` の枠と同じ大きさ（3 ページ幅にしない。クリップ用の親ビューのずらしもしない）。
- iOS: `scrollView.isScrollEnabled = true`、`bounces = true`、`showsVerticalScrollIndicator = false`、`scrollsToTop = false`、
  `contentInsetAdjustmentBehavior = .never`。ピンチズームは無効のまま。
- macOS: スクローラを出さない（ラッパーの CSS で `scrollbar-width: none`）。`allowsMagnification = false`。
- 読み込むのは `epub://<id>/_reader/scroll?start=<spineIndex>`。`ScrollDocument`（EPUBRenderer、`SpreadDocument` の隣）が生成する
  `text/html` の文書で、`<html data-reader-scroll>` の下に、先頭の境界 `#__reader_head`、上の余白 `#__reader_runway`、章の iframe を
  並べる `#__reader_stage`、下の余白 `#__reader_tail`、末尾の境界 `#__reader_foot` をこの順に持つ。`overflow-anchor: none`
  （スクロールアンカリングは使わない。07 §2.3）。
- 境界の高さは上 / 下のインセット。スクロール位置 0 で最初の章の上端が読む行に来て、最下端で最後の章の下端が下のインセットの
  上に来る。境界が無いと、本の最初と最後のインセット分がバーの下から出せない。
- 章の iframe は `scrolling="no"`、`display: block; width: 100%; border: 0`、高さは章の内容の高さ。`data-spine-index` /
  `data-spine-steps` を持つ（見開きラッパーと同じ属性）。
- `reader.js` はラッパー文書（`html[data-reader-scroll]`）で「スクロールコントローラ」として動く。見開きコントローラ
  （02-rendering §4.1）と同じ形で、Swift には今までと同じ API と、§4.3 の追加分を見せる。iframe の中の `reader.js` は
  今までどおり Swift にメッセージを送らず、ホスト（コントローラ）に渡す。

### 4.2 章の CSS

章の文書には今までどおり `reader-before.css` / `reader-after.css` を注入する。`layout` の引数に `scrolled: true` を足し、
`reader.js` が `<html data-reader-layout="scrolled">` を付ける。この属性があるとき:

- 多段組を外す。`html { height: auto; overflow: hidden }`（iframe の中ではスクロールしない）。
- 本文の箱は `html` に付ける: 左右中央、`max-width` は `scrolledTextWidth` em、左右の `padding` は `pageMargins.horizontal`。
  単位は `rem` でなく `em`（WebKit は、ルート要素自身の `max-width` の `rem` を、リーダーが掛けた文字サイズの倍率より前の
  大きさで解決する。`rem` だと `fontScale` を変えても幅が変わらなかった）。`body` に付けないのは、出版物の CSS が `body` の
  幅や余白を決めていることが多いため。
- 章の上下に `pageMargins.vertical × 2` の余白（既定 20 → 40 px。章と章の間は 80 px）。区切り線は引かない。
- 画像と SVG は `max-width: 100%`、`max-height` はページの高さ P（1 画面に収まる。ページ表示と同じ扱い）。章の高さが P に
  依存するので、P は高さのキャッシュのキーに入る（§6.3）。
- 改ページの指定（`break-before` など）は効かない（多段組が無いので何も起きない）。

**ビューポート単位**: iframe の中の `vh` は iframe の高さを指す。`height: 100vh` の要素（表紙に多い）があると、iframe を内容の
高さに合わせるたびに内容がまた伸び、止まらない。次の規則で止める。

- 章の文書は、スタイルシート（`@import` と入れ子の規則を含む）と `style` 属性にある `vh` / `svh` / `lvh` / `dvh` / `vb` /
  `vmin` / `vmax` の長さを、P を基準にした px に書き換える（`100vh` は P、つまり 1 画面分。`vmin` / `vmax` は本文の幅と P の
  小さい方 / 大きい方）。元の値は覚えておき、P が変わる再レイアウトでは元の値から書き直す。`url(…)` を含む値は触らない。
  書き換えた後の章は iframe の高さに依存しないので、高さは内容に合う。
- 書き換えで消えない依存（`@media (min-height: …)` など）のために、次の規則も残す: iframe の高さを内容に合わせた直後に
  内容がまた伸びる、が 3 回続いたら、その章を「ビューポートに依存する章」とみなして高さを最初の内容の高さ H1（iframe が P の
  ときの高さ）に固定し、以後その章の高さは追わない（`chapterHeight` も H1 のまま）。この場合、H1 に収まらない内容は
  見えない。計測用 WebView でも同じ手順（S3）。

S1 の実装で改めた点: 最初の設計は固定の規則だけだった。それだと、`100vh` の要素の後ろに内容がある章（表紙と題名、章扉と本文）で、
固定した iframe の中の `100vh` が H1 になり、後ろの内容が H1 − P だけフレームの外に出て見えなくなる（Codex のレビューの指摘。
fixture の表紙の下の説明文が切れていた）。

### 4.3 コントローラの API（Swift → JS、追加分）

| 関数 | 役割 |
|---|---|
| `layout({…, scrolled: true, insets, pageHeight, heights, generation, holdFar})` | 窓の全 iframe に `layout` を転送し、高さを取り直す。`heights` は章ごとの高さの見積もり（§5.2）。`generation` はこのレイアウトの番号（下記）。`holdFar` は VoiceOver が動いているか（遠い章を外さない。§5.1）。`{writingMode}` を返す |
| `showLocation({spineIndex, cfi \| fragment \| offset})` | 行き先が窓の中ならその位置へスクロールし、外なら窓を作り直す（§8.1）。`{spineIndex, offset}` を返す |
| `scrollBy({pages \| lines, animated})` | 1 画面分 / 数行分のスクロール（§8.2） |
| `locationAtReadingLine()` | 読む行の `{spineIndex, offset, chapterHeight, cfi}` |
| `setEstimates(heights)` | 計測が進んだときの見積もりの更新。余白は静止しているときに直す（§5.4） |
| `trimWindow()` | 窓を表示領域にある章とその前後 1 章に縮める（メモリ警告。§12） |
| `setInteraction({active})` | 読者の操作が進んでいるかを Swift から伝える（§5.6） |
| `windowContains(spineIndex)` / `holds(spineIndex)` | その章が今の窓にあるか / このスクロール文書が持つ章か（線形でない章を単独で開いた文書は 1 章しか持たない。持たない章へのジャンプは、Swift が別のスクロール文書を読み込む） |

JS → Swift の追加メッセージ:

| type | payload | 発火 |
|---|---|---|
| `scrolled` | `{spineIndex, offset, chapterHeight, visible: [spineIndex], atEnd, atStart, cfi, rest, loaded, generation}` | スクロール中、100 ms に 1 回まで。静止したとき（§5.6）に `rest: true` でもう 1 回。Swift がページ番号・進捗・位置（`cfi`）を更新する |
| `scrolling` | `{active, user}` | スクロールの始まりと終わり。`user` は読者の操作によるものか（S2） |
| `chapterHeight` | `{spineIndex, height, generation, fixed}` | 章の高さが決まった / 変わった（読み込み、フォント、画像、再レイアウト）。Swift がキャッシュに書く。`fixed` はビューポートに依存する章（§4.2） |
| `chapterWritingMode` | `{spineIndex, writingMode}` | 章の `ready`。縦書きならセッションがページ表示に切り替える（§1） |

**レイアウトの番号**: `layout` と窓の作り直しのたびに Swift が `generation` を増やして渡し、コントローラは `scrolled` /
`chapterHeight` にそのとき有効な番号を付けて返す。Swift は今の番号と違うメッセージを捨てる。古い幅やフォントで読み込みかけて
いた iframe の高さが、設定変更の後に届いて新しいキャッシュに入るのを防ぐ（`PaginationCache` の世代の検査は、計測した時点の
世代を渡して初めて効く）。

`pageFor` / `rectsFor` / `setHighlights` / `setTransientHighlight` / `currentSelection` などは、見開きコントローラと同じく
CFI の spine ステップで iframe を選んで転送する。窓に無い章への `setHighlights` は覚えておき、その章を読み込んだときに描く。

## 5. 窓と余白

### 5.1 窓

- 窓は連続した線形の章。開いた直後は、行き先の章 1 つと、その前後 1 章ずつ。
- **足す**: 表示領域の上端から窓の先頭までが 2P より近くなったら前の章を、下端から窓の末尾までが 2P より近くなったら
  次の章を読み込む。1 つ読み込み終わってから次を判断する。
- **外す**: 表示領域から 8P より遠い章を、静止しているとき（§5.6）に外す。表示領域に一部でも入っている章とその前後 1 章、
  選択のある章は外さない。VoiceOver が動いている間は、この規則では外さない（フォーカスのある章を JS から知る手段が無い）。
- **上限**: 窓の章が 24 を超えたら、スクロール中でも表示領域から最も遠い章から外して 24 に戻す。止まらずに読み進める間、
  通り過ぎた章が残り続けないようにする。外し方は §5.3 と同じで、スクロール位置は書かない（スクロール中に外す場合は未計測。§14）。
  1 章あたりのメモリは約 1 MB（07 §2.1）なので、24 章で 25 MB 前後。
- 1 章が巨大でも 1 つの iframe のまま（07 §2.1: 高さ 578,714 px の章で +32 MB、描画は見えている所だけ）。
- 表示領域に 24 より多くの章が入る本（ごく短い章が続く）では、表示領域にある章を優先し、上限を超えてよい。
- 窓が上限に達しているとき、章を足すのは「足した結果、上限の規則で外れるのが反対側の端の章になる」場合だけ
  （`scroll-core.js` の `admits`）。1 ページよりずっと短い章が続く本では、前後 2P の先読みが 24 章より多くを求める。
  この条件が無いと、足した章が最も遠い章としてすぐ外れ、また足され、読者が何もしなくても読み込みを繰り返す
  （Codex のレビューで再現: 高さ 106 px の章 60 個で、静止中の 2 秒に 500 回以上の読み込み）。

### 5.2 余白

- 上の余白の高さは「窓より前にある線形の章の高さの合計」、下の余白は「窓より後の章の高さの合計」。各章の高さは、
  計測済みならその値、未計測なら見積もり（§6.2）。
- これでスクロール位置は本全体の中の位置にほぼ一致し、文書の高さは本全体の高さにほぼ一致する。
- 下の余白は 0 より小さくしない。足した章が残りの見積もりより長ければ、余白は 0 になり、文書がその分伸びる（読む行より下の
  変化なので、読んでいる行は動かない）。
- 最後の線形の章が窓に入ったら、下の余白は 0 にする（見積もりが大きかった分を残すと、本の後ろに空白ができる）。表示領域が
  その余白の中にあった場合（§5.5）は、最後の章の末尾に寄る。
- 上の余白が足りないとき（0 でも補正が残る）の扱いは §5.4。
- **上限**: 上の余白と下の余白は、それぞれ 8,000,000 px までにする（`scroll-core.js` の `MAX_SPACE`）。WebKit は 2^25 px
  （33,554,432 px）より高い文書を組めない（実測: 余白 30,000,000 px では位置も描画も正しく、40,000,000 px では清算が
  終わらなかった）。余白が受け持つのは、静止から次の静止までの間に窓へ入る章の分だけで、それよりはるかに小さい。
  上限に掛かっている間、スクロール位置は本全体の中の位置と一致しないが、スクロールインジケータは出さず、位置はすべて
  「章 + 章の中の距離」で扱うので、見える違いは無い。清算（§5.4）の目標もこの上限つきの値。

### 5.3 位置の補正

読んでいる行より上のレイアウトが変わったとき（上に章を足す、上の章の高さが変わる、読んでいる章の中で読む行より上が伸び縮みする、
上の章を外す）、読んでいる行が動かないようにする。

- **スクロール位置は書き換えない。上の余白の高さで帳尻を合わせる。** 指や慣性でスクロールしている間、スクロール位置は
  UI プロセスが決めていて、ページが書いた位置は古い値で上書きされる。その間ページは要らない章を読み込み、違う場所を描き、
  基準を取り違える（07 §2.4: 空白の画面、2,528 px のずれ）。余白の高さを変えるのはレイアウトだけの変更で、この競合が起きない。
- 手順: 読む行にある文字を基準として覚えておく。レイアウトが変わったら、基準が文書の中で動いた量 d を求め、
  上の余白を d だけ縮める（d が負なら伸ばす）。
- **基準は要素でなく文字の位置（Range）。** 読む行のすぐ下を `caretRangeFromPoint` で引いた Range（§7 の位置と同じ引き方）の
  矩形の上端を使う。段落の要素を基準にすると、同じ段落の中で読む行より上にあるインライン画像が後から伸びたとき、段落の上端は
  動かないので補正が 0 になり、読んでいる行だけが下がる（スパイクは章の先頭へのブロック追加しか測っていない）。文字が無い
  場所（画像だけの画面）では、読む行にかかる要素の上端を使う。
- **基準の位置は文書座標（ビューポート内の位置 + `scrollY`）で比べる。** スクロール中の `scrollY` は古い値に戻る
  ことがあるので、ビューポート内の位置を比べると同じ補正を 2 回かける（07 §2.3）。窓を動かす判断（§5.1 の距離）も、
  章の iframe と基準の文書座標から求め、`scrollY` 単独の値に頼らない。
- 基準は `scroll` のたびに、読む行から外れていれば引き直し、そのときの文書座標を覚える（変化の前の位置は、変化が起きてから
  では取れない）。表示領域に章が 1 つも無いとき（窓を追い越した。§5.5）は、窓の先頭の章の上端を基準にする。
- **上の章を外すときは、外すのと同じレイアウトの中で、上の余白を章の高さだけ先に伸ばす。** 後から伸ばすと、間のレイアウトで
  文書が縮み、最下端付近ではスクロール位置が切り詰められて行が飛ぶ（07 §2.3）。
- 章の高さは、各章の `documentElement` を `ResizeObserver` で見て合わせ直す。`load` の後にフォントが当たって高さが変わるのは
  ほぼ全章で起きる（07 §2.2）。
- **章の iframe が縮むときは、縮んだ分を補正が終わるまで `#__reader_stage` の `padding-bottom` に持たせる。** iframe を
  縮めた時点のレイアウトで文書が短くなり、最下端ではブラウザがスクロール位置を切り詰める。補正（余白を伸ばす）はその後
  なので、読んでいる行が縮んだ分だけ動く（S1 の実測で見つかった。外すときと同じ理由）。補正の後で `padding-bottom` を 0 に戻す。
- 読む行に文字が無いとき（読み込み中の章、章の最後の行より下の空き）は、次の章が画面内で始まっていればその先頭を基準に
  する（本の最後から 2 番目の章の高さが決まる間、読者が見ているのは次の章の始まりである）。
- 読んでいる行より下の変化（下に章を足す、下の章の高さが変わる、下の章を外す）は、下の余白の高さを同じ量だけ逆に変える
  （0 が下限。§5.2）。読む行より下の変化なので、文書の高さが変わる場合も読んでいる行は動かない。

### 5.4 余白の清算

章を足すとき、上の余白は実際の高さだけ縮む。その章の見積もりが実際と違っていれば、余白は「窓より前の章の高さの合計」から
その差だけずれる。計測が進んで見積もりが変わったときも、窓の中の章の高さが読む行より上で変わったとき（§5.3。余白で
受けた分だけ、余白が合計からずれる）も同じ。

- ずれは、静止しているとき（§5.6）に直す。手順: 基準の**ビューポート内の位置** y0 を取る → 上の余白を正しい値にする →
  レイアウトさせて基準のビューポート内の位置 y1 を取り直す → `scrollTo(scrollY + (y1 − y0))`。
- 余白を変えた量をそのまま `scrollBy` に渡さない。文書の最下端で余白を縮めると、文書が縮んだ時点でスクロール位置が先に
  切り詰められ、同じ量をもう一度引くと 2 重に動く。静止中は `scrollY` が信頼できるので、ここではビューポート内の位置で比べる
  （§5.3 の文書座標は、`scrollY` が古い値に戻るスクロール中のためのもの）。
- 実測との関係: 静止中に `scrollBy` で位置を合わせる操作は、切り詰めの起きない場合について iOS と macOS で 0 px・ちらつき
  なしだった（07 §2.3 の manual の列）。最下端では、文書座標で比べる manual の補正は iOS で 11,329 px、macOS で 4,227 px ずれた（同）。
  上の手順（ビューポート内の位置で取り直す）は測っていないので、S1 のテストに最下端での清算を入れる（§13）。
- 全章の高さが計測済みで、計測値が表示したときの高さと一致していれば、ずれはほぼ出ない（計測は本を開いて数秒で終わる。
  一致するかは未検証。§6.2）。
- 本の先頭の章が窓に入った時点で余白が余っている（見積もりが大きかった）と、最初の章の上に空白が残る。止まっていれば
  その場で清算する。スクロール中なら止まるまで残り、止まったときに清算する（空白を見ていた場合は最初の章の先頭に寄る）。
- **余白が足りないとき**: 上の余白が 0 でも補正が残ることがある。見積もりが小さかった章を、止まらずに本の先頭近くまで
  さかのぼったときと、最初の章を読んでいる最中に、その章の読む行より上が伸びたとき（計測の済み / 未済によらない）。
  このときもスクロール位置は書かない。足りない分 n は `#__reader_stage` の `margin-top: −n` で受ける（章の並びの先頭 n px が
  文書の原点より上に出る）。静止したら、上の手順で `margin-top` を 0 に戻して位置を合わせる。それまでに本の先頭まで
  スクロールすると、最初の章の先頭 n px が見えないが、止まった時点で直る。負のマージンで受ける方法は未計測（§14）。

### 5.5 窓を追い越したとき

速いスクロールで、章の読み込みより先に表示領域が余白へ入ることがある。その間は背景色が見える。窓は今までどおり 1 章ずつ
表示領域へ向かって伸ばす（窓は連続したまま）。離れた場所だけを先に読み込むことはしない。空白がどれだけ出るかは S1 の実機確認で
見る（07 §2.5 の「極端に速いスクロール」）。

### 5.6 静止の判定

スクロール位置を書く操作（清算、ジャンプ、再レイアウト後の位置合わせ）と、上限によらない章の除去は、静止しているときだけ行う。
「`scroll` イベントが 150 ms 来ない」だけでは静止と判断しない: 指を置いたまま止めている間も条件を満たし、そこで位置を書くと、
ドラッグを再開したときに §5.3 の競合になる。

- **iOS**: `WKWebView.scrollView` の `isTracking` / `isDragging` / `isDecelerating` を 0.05 秒ごとのタイマーで読む。どれかが
  真の間は操作中。Swift が変わり目で `setInteraction` を送る。`UIScrollViewDelegate` は使わない（WKWebView のスクロール
  ビューの delegate は WebKit が使っていて、差し替えると WebKit の処理を奪う）。
- **macOS**: スクロールホイールのイベントの `phase` / `momentumPhase`（EPUBUI が既にローカルモニタで見ている）で、ジェスチャと
  慣性の始まりから終わりまでを操作中とする。位相の無いホイール（マウス）は、最後のイベントから 150 ms を操作中とする。
- プログラムのスクロール（`goForward()` のアニメーション、↑ ↓）は、コントローラが始めてから `scrollend`（無ければ
  位置が目標に着いて 150 ms）までを進行中とする。
- 静止 = 操作中でなく、プログラムのスクロールも進んでおらず、最後の `scroll` イベントから 150 ms 経っている。最後の条件は、
  Swift から `setInteraction` が届くまでの間（iOS は最大 0.05 秒、macOS のマウスホイールは位相が無い）を埋める。
  公開の `isScrolling` / `scrolling(_:)` は `goForward()` などのアニメーションを含まないので、この判定には使わない。
- 静止を待つ処理（清算、除去、メモリ警告での縮小）は、静止になった時点で 1 回ずつ行う。

**操作を止める**: ジャンプ（§8.1）と再レイアウト（§11）は静止を待たず、先に操作を止めてから位置を書く。

- iOS: `scrollView.stopScrollingAndZooming()` で慣性を止める。指が触れている場合は `panGestureRecognizer` を一度無効にして
  追跡を打ち切る。`isTracking` / `isDecelerating` が偽になったのを確かめてから進む。
- macOS: 進行中のジェスチャと慣性の残りのホイールイベントを、その位相が終わるまで WebView に渡さない。
- 止めた後に、位置（CFI）を取り直す（止めるまでに進んだ分を反映する）。

実測（§14、§16）: iOS は Simulator で、慣性の最中のジャンプで慣性が止まり、その後スクロール位置が動かないことを記録で
確かめた（指が触れたままの場合は実機で確かめる）。macOS は、位相つきのホイールイベントを合成するテストで、残りの慣性の
イベントを渡さなければスクロールが止まることを確かめた（WebKit は慣性を自分で続けない）。

## 6. 高さの計測とページ番号

### 6.1 仮想ページ

- 1 ページ = ページの高さ P。章 i の高さを h とすると、その章のページ数は `max(1, ceil(h / P))`。章の中のページ j は、
  章の上端からの距離が `[jP, (j+1)P)` の範囲。
- 章ごとに切り上げるので、章の最後のページは P より短いことがある（ページ表示で章末のページに空きがあるのと同じ）。
- `BookPagination` の形は変えない（章ごとの `pageCount`、`firstPage`、推定かどうか）。`currentPage` は読む行のあるページ。
- `go(toPage:)` は、そのページの上端（章の上端から jP）を読む行に合わせる。
- **本の末尾**: スクロールは、最後の章の下端が下のインセットの上に来た所で止まる（末尾の境界。§4.1）。そこでは読む行は
  最後の章の下端から P だけ上にあり、それより後ろのページ（最後の章の最終ページ。最後の章が短ければその前の章の終わりの
  数ページも）の上端は読む行に届かない。そこで、最下端にいるとき（`isAtEnd`）は `currentPage` を最後のページ、
  `totalProgression` を 1 とする。届かないページへの `go(toPage:)` / `go(to:)` は最下端で止まる。線形でない章を単独で
  見せるとき（§1）も同じ。

### 6.2 計測

- `PaginationService`（事前ページ化用の非表示 WebView）が、スクロール表示のときは各章を `scrolled: true` で `layout` し、
  内容の高さを `PaginationCache` に書く。順序と打ち切りはページ表示と同じ（02-rendering §8.1）。隣接章のスナップショットは撮らない。
- 表示用 WebView が読み込んだ章の高さ（`chapterHeight`）もキャッシュに書く。両方ある章は表示用の値を優先する。
- 未計測の章の高さは見積もり: `BookPagination` の今の推定（文字数 ÷ 1 ページあたり文字数）で出したページ数 × P。
  1 ページあたり文字数は、計測済みの章の「文字数 ÷ (高さ ÷ P)」から学習する（規則は 02-rendering §5.2 のまま）。
- 計測が進むたびに `paginationUpdated` を出し、コントローラに `setEstimates` を送る。

非表示の WebView で測った高さが、表示したときの高さと一致するかは未検証（スパイクでは、画面外の iframe で測った高さが
フォント適用前の値のままだった。07 §2.2）。ずれても §5.3 と §5.4 が吸収するが、ページ数が後から少し動く。S3 で確かめる。

### 6.3 キャッシュのキー

`LayoutKey` に表示方式を足す。スクロール表示のキーは「本文の幅（整数 px に丸める）、ページの高さ P（同）、
`ReaderSettings.layoutKey`（フォント、サイズ、行間、余白、`scrolledTextWidth`）」。キャッシュに置くのは章の高さで、ページ数は
読むときに P で割って出す。

P をキーに入れるのは、画像の高さの上限が P だから（§4.2）: 縦長の画像のある章は、幅が同じでも P が変わると高さが変わる。
表示領域の高さやインセットが変わったら、ページ表示と同じく新しいキーで計測し直す（全章で 1〜2 秒。07 §2.2）。P に上限を
受けた画像の無い章の高さを P の違うキーへ持ち越す最適化は、後で足せる（章ごとに「P に依存したか」を記録する）。

## 7. 位置

- 読書位置は今までどおり CFI。スクロール表示では、読む行にある最初のテキストの CFI（章の iframe の中で、読む行のすぐ下を
  `caretRangeFromPoint` で引く。テキストが無ければ今の `cfiForPage` と同じ順で要素へ下がる）。
- 位置の復元（開いたとき、設定変更、リサイズ、方式の切り替え、WebContent の復旧）は、その CFI の文字の上端を読む行に合わせる。
- ページ表示とスクロール表示の間で位置は互換（どちらも CFI）。他の端末がどちらの方式で保存した位置でも開ける。
- 方式を切り替えると、位置は切り替え先の規則で取り直される。ページ表示の `position` は「表示しているページの最初の文字」
  なので、スクロール表示でページの途中の文字を読む行に置いていた場合、ページ表示に切り替えるとその文字を含むページが出て、
  位置はページの先頭に移る。そこからスクロール表示に戻すと、読む行はそのページの先頭になる（最大で 1 ページ分戻る。
  元の文字は画面の中に残る）。往復で元の行に戻すことはしない。
- `position` の更新と `positionChanged` は §3.3 の頻度。`ReadingPosition` の章内・全体の進捗は仮想ページから。

## 8. 移動

### 8.1 ジャンプ

`go(to:)` 系は `showLocation` を呼ぶ。

- 先に操作を止める（§5.6）。
- 行き先の章が窓にあれば、その章の中の位置を求めて、そこが読む行に来るようにスクロールする。
- 窓に無ければ、窓を作り直す: 今の画面を `relayoutSnapshot` に置き、章の iframe を全部外し、上下の余白を行き先の章に合わせ、
  行き先の章（と前後 1 章）を読み込み、位置を合わせてから画像を外す。
- 終わったら `positionChanged`、可視ページが変わっていれば `navigated`。

### 8.2 1 画面分・数行分

- `goForward()` / `goBackward()`: `P − 重なり` だけアニメーションでスクロールする。重なりは本文 1 行分（文字サイズ × 行間）。
  本の先頭 / 末尾では止まる。動いた量が 0 なら `navigated` は出さない。
- ↑ ↓: 本文 3 行分。読者のスクロールとして扱う（`scrolling` が出る）。
- Home / End: 読む行のある章の先頭 / 末尾へのジャンプ。
- アニメーション中に上へ章が足されても、位置の補正は余白で行うので、アニメーションは途切れない。

## 9. 入力

- iOS のスクロールは WKWebView の `UIScrollView` にそのまま任せる（慣性、端でのバウンス）。EPUBUI はスワイプの
  ジェスチャを付けない。タップは `reader.js` の `tap` をそのまま `tapped(_, zone: .center)` にする。
- macOS のトラックパッド / ホイールも WKWebView に任せる。EPUBUI の「スワイプをめくりのドラッグに変える」処理
  （03-api §4.3）はスクロール表示では入れない。横方向の動きは捨てる。
- キーは `ReaderKeyAction` に「数行スクロール」を足し、対応表を §0 のとおりにする。進捗スライダーにフォーカスがある間は
  リーダーがキーを取らない規則は同じ。
- VoiceOver は WKWebView 標準のスクロールに任せる。ページ表示で入れている `accessibilityScroll` の差し替えは使わない。

## 10. 既存の機能

| 機能 | スクロール表示での扱い |
|---|---|
| 選択 | 章の iframe の中の選択をそのまま使う。章をまたぐ選択はできない（縦書き見開きと同じ制限）。編集メニューへの項目追加は同じ。選択のある章は窓から外さない（§5.1）。窓を作り直すとき（ジャンプ、再レイアウト）は、ページ表示で文書を読み直すときと同じく選択を解除して `selectionChanged(nil)` を出す |
| 注釈の描画 | 章ごとに `setHighlights`。窓に入った章に、その章の分を描く |
| 注釈のタップ | 同じ（`annotationTapped`）。矩形は枠の座標 |
| 検索 | 検索は EPUBCore なので同じ。`show(_:)` は結果の位置へジャンプして一時ハイライトを描く。次のジャンプか、ハイライトが表示領域から出たスクロールの終わりで消す |
| 内部リンク | ジャンプ（`navigated(.link)` → `internalLink`） |
| 脚注 | 同じ（`noteref`）。同じ文書の脚注の `aside` を隠す規則も同じ。別の文書の脚注を読む間に動いたら出さない規則は、ページ番号でなくスクロール位置で判定する（タップから後に `scrolled` が 1 つでも届いていたら捨てる。同じ仮想ページの中でも矩形は古くなる） |
| 画像のタップ | 常に `imageTapped` |
| 同梱の注釈 | 同じ |

## 11. 再レイアウトと切り替え

- **設定、幅、高さ、インセットの変更**: 操作を止め（§5.6）、止めた後の CFI を覚え、画面を `relayoutSnapshot` に置き、
  `generation` を増やして窓の全章を `layout` し直し、余白を新しい見積もりで作り直し、CFI を読む行に合わせて、画像を外す。
  キーが変わるので計測は新しいキーでやり直す。高さとインセットだけの変更でも組み直すのは、P が画像の高さの上限だから（§6.3）。
- **表示方式の切り替え**（`settings.layout` の変更、§1 の縦書きの検出）: 操作を止め、今の CFI を覚え、`relayoutSnapshot` を置き、
  WebView の設定（§4.1 / 02-rendering §1）を切り替え、もう一方の文書（章の文書 / 見開きラッパー / スクロール文書）を
  読み込んで CFI で位置を戻す。
- macOS のウィンドウリサイズ中の 150 ms デバウンスは同じ。

## 12. 復旧とメモリ

- WebContent プロセスが落ちたら、`position` の CFI でスクロール文書を読み直す（回数の上限は 02-rendering §9 と同じ）。
- メモリ警告では、窓を表示領域に一部でも入っている章とその前後 1 章に縮め（`trimWindow`）、計測を一時停止する。静止を
  待たない: 外し方は §5.3 と同じで、スクロール位置を書かない。選択のある章が外れるときは、選択を解除して
  `selectionChanged(nil)` を出す。

テスト:

- 位置の安定は、スパイクと同じ方法（読む行の文字の位置 + 帯のスナップショット）を `EPUBRendererTests` に移す: 上に章を足す、
  上の章の高さが変わる、読んでいる章の中で上が伸びる、**読んでいる段落の中で上のインライン画像が伸びる**、上の章を外す

  `document.visibilityState` を確かめ、フレーム待ちに期限を付ける。隠れていた / 期限が切れたときは失敗にする（成功にも、
  止まったままにもしない）。これらのテストは直列で走らせる。

    実行ループが止まり、テストの途中でプロセスが終了コード 0 で終わる。ウィンドウのレベルを上げても、他のアプリの全画面の
    ウィンドウの下では隠れたままになる。
  - 代わりに、テスト用の WebView で WebKit のウィンドウ遮蔽の検出を切る（SPI `-[WKWebView _setWindowOcclusionDetectionEnabled:]`。
    テストの `visibleHost`）。ウィンドウが他のウィンドウの下にあってもページは `visible` で、フレームが約 60 fps で来る。
  - 帯の絵は `WKWebView.takeSnapshot` でなく、ウィンドウサーバーから読む（`CGWindowListCreateImage`。テストの
    `windowBand`）。macOS の `takeSnapshot` は画面の絵でなく、要求の時点でレイアウトを強制して描いた絵を返すので、
    どのフレームにも無い状態が写ることがある（07 §4.2）。この関数は Swift には公開されなくなっているので `dlsym` で呼ぶ。
    無くなったら試行は失敗する（成功にはしない）。
  - 読む行の文字の位置をフレームごとに読むときは、`requestAnimationFrame` の中で読まない（そこで読むと、補正する
    `ResizeObserver` より前にレイアウトを強制し、実際には描かれない位置が見える）。rAF から `MessageChannel` で送った
    メッセージの中、つまりそのフレームの描画の後で読む。
- macOS のトラックパッドは、位相と慣性の位相を持つスクロールホイールのイベントを合成して WebView に渡すテストにする
  （`ScrollWheelTests`。`CGEvent` を `NSEvent` に変えて `scrollWheel(with:)` へ。セッションの `WheelInteraction` と WebKit の
  スクロールの両方を通る）。本物のトラックパッドの慣性の曲線は再現しない。
- 窓の規則（どの章を足す / 外すか、上限）、仮想ページの算術（末尾の規則を含む）、余白の清算量、静止の判定の状態遷移は、
  WebView 無しで検証できる純粋な関数に分ける。
- 方式の切り替えの往復（§7）、レイアウトの番号の違う `chapterHeight` を捨てること、ビューポートに依存する章の高さが
  止まること（`height: 100vh` の表紙の fixture）をテストにする。
- 指でのスクロールは自動テストにしない（Simulator へのスワイプ注入は外の道具が要る）。代わりに、ReaderDemo に記録モードを
  足す: 本物の `ReaderSession` とスクロールコントローラで本を開き、スパイク 9 と同じ記録（フレームごとの位置、補正、読み込み、
  帯のスナップショット）を書き出し、外からスワイプを入れて `analyse-fling.py` で読む。スパイク 9 は専用のコントローラと
  固定の余白で動くので、製品のコードの回帰は検出できない（方式の根拠としてだけ残す）。使い方は

### 16.3 S1 で残したこと

- 実機での確認（滑らかさ、描かれないコマの見え方、指が触れたままのジャンプ、本物のトラックパッド）。
- 上限（24 章）で、本物の指や慣性の最中に章が外れる場合の記録。
- iOS で操作を止める手順は、`stopScrollingAndZooming()` と pan の無効化の後、0.25 秒待っても `isTracking` などが偽に
  ならなければそのまま進む（ジャンプを取りやめない）。指が触れたままで偽にならないことがあるかは、実機で確かめる。
- 余白の上限（8,000,000 px）は、静止したときの目標値にだけ掛かる。1 回の操作の間に上の章が外れ続けると、その間は余白が
  目標を超えて伸びる。WebKit の上限に届くには、一度も止まらずに 2,500 万 px（毎秒 20,000 px で 20 分）進む必要があるので
  対処していない。
- `@media (min-height: …)` などで iframe の高さに依存し続ける章は、§4.2 の予備の規則で高さを固定する。収まらない内容は
  見えない（実例は未確認）。
- `scroll` イベント 1 回の処理は記録で平均 0.2 ms、最大 4 ms（Simulator）。描かれないコマの原因ではなかった。
